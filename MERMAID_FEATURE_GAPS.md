
### Relationship vocabulary

- Aggregation `o--` — could distinguish weak ownership (e.g., `optional` message fields
  vs. required ones).


### Layout / interaction / styling — none emitted

- `click` / `link` / `callback` (could deep-link to the source `.proto` in a repo, or to
  API reference docs).
- `style ClassName fill:…`
- `classDef`, `cssClass`, `:::shorthand`
- `%% comments` in the output (could carry a "generated by …" provenance header).

### Other config-frontmatter keys

The compiler doesn't expose `securityLevel`, theme/`config.theme`, or the broader
[`config.class.*`](https://mermaid.js.org/config/configuration.html) knobs.

## Most worthwhile next bets

In rough order of signal-to-effort, matching CLAUDE.md's stated direction:

1. **Leading-comment → `note for`** — the only un-rendered information *already in the
   descriptor*; biggest signal/effort win.
2. **`map<K, V>` rendering** — the compiler already filters synthetic map-entry messages;
   rendering as `Map~K,V~` with Mermaid generics is the natural form.
3. **Streaming RPC markers** — `Stream~Req~` generics in the method signature, or a method
   classifier, beats prose.
4. **Nested-leaf collision disambiguation** via `class Inner["Parent.Inner"]` labels —
   Mermaid supports it natively, no rendering hack required.
